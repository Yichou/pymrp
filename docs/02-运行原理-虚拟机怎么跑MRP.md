# 02 · 运行原理：虚拟机怎么跑 MRP

这篇是"想自己写一个 MRP 模拟器"的核心。所有内容都经过实机验证（A 级），
并给出对应的可执行验证方法。

---

## 1. 为什么必须真执行 ARM

`.mrp` 包里的 `.ext` 条目（典型是 `cfunction.ext`，解压后约 331 KB）是**纯 ARM 机器码**，
开头就是 `push {r3,lr}` 之类的指令。Mythroad 层的全部业务逻辑——解包、资源管理、
UI 框架、字节码解释器——都在里面。

所以有且只有三条路：

| 路线 | 做法 | 后果 |
|---|---|---|
| ✅ 真执行 | 用 ARM 执行引擎（Unicorn/QEMU 内核）跑它 | 与官方二进制完全兼容，无需逆向 |
| ❌ 自己写 ARM 解释器 | 逐条实现 ARM/Thumb 指令 | 理论可行，性能差 2~3 个数量级，且要处理全部指令编码 |
| ❌ 重写 Mythroad | 用宿主语言重写整个运行时 | 等于逆向 331 KB 的 ARM 代码，工作量无上限，且必然行为不一致 |

本项目与 vmrp 都选第一条。**这也是这套体系能"复活"的关键**：
只要造出执行环境和 API，原始二进制就能跑，不需要任何逆向。

---

## 2. 内存布局

固定 8 MB 线性地址空间，三块区域，**地址是硬约定，改一个字节就会崩**（C 级，
来自 `vmrp/header/vmrp.h`，A 级实测可跑）：

| 区域 | 起始 | 大小 | 结束 | 用途 |
|---|---|---|---|---|
| 代码段 | `0x00080000` | 1 MB | `0x00180000` | 加载 `cfunction.ext`，函数表也在这里 |
| 栈 | `0x00180000` | 1 MB | `0x00280000` | SP 初始指向 `0x0027FFF0` 附近 |
| 堆 | `0x00280000` | 6 MB | `0x00880000` | `mr_mem_get` 从这里切 |

```
0x00000000  ┌─────────────┐
            │  未映射      │  ← 空指针区，访问即崩（正好当保护页）
0x00080000  ├─────────────┤
            │ 代码 + 函数表 │  1 MB
0x00180000  ├─────────────┤
            │    栈        │  1 MB，向下增长
0x00280000  ├─────────────┤
            │    堆        │  6 MB，first-fit 分配
0x00880000  └─────────────┘
```

### 2.1 堆分配器

第一版做个 **first-fit 空闲链表**就够了。块头至少要有：

```
struct block {
    uint32 size;     // 含块头的总大小
    uint32 free;     // 1 = 空闲
};
```

对齐 8 字节（ARM EABI 要求 8 字节对齐的 `double`/`long long`，且 ext 里可能有 NEON 前的
对齐假设）。`mr_mem_get(0)` 要返回有效指针而不是 NULL，有些应用会这么试探。

### 2.2 零拷贝内存映射（性能关键）

不要在每次 API 调用时把模拟内存拷进 Python/宿主缓冲。**把模拟内存映射成宿主可直接
访问的 buffer**：

- C 版（vmrp）：`mem_map_ptr` 拿到宿主指针，直接当普通内存用；
- Python 版（本项目）：`Unicorn.mem_map` 后保留 `bytearray` 引用，用 `struct`/`memoryview`
  直接读写，避免 `uc.mem_read/mem_write` 的跨语言往返。

这一步对性能影响极其显著：`uc.mem_read` 每次有固定开销，逐像素操作会被放大上百万次。

## 3. 核心机制：用内存地址当 syscall 号

这是整个体系最巧妙的设计，也是实现模拟器时**必须完全照抄**的部分。

### 3.1 问题

ARM 代码要调用宿主（C 写的 SkyEngine）里的函数。但它是机器码，不是可重定位的 ELF，
没有符号表、没有动态链接。怎么找到 200 多个宿主函数？

### 3.2 解法：函数表 + 可执行地址桩

宿主在内存里建一张表，**每个槽位 4 字节，里面写这个槽位自己的地址**：

```
表基址 B = 0x00080000 + 0x1000（示意）

B + 0x000:  00 10 08 00    →  0x00081000   (mr_mem_get)
B + 0x004:  04 10 08 00    →  0x00081004   (mr_mem_free)
B + 0x008:  08 10 08 00    →  0x00081008   (mr_open)
...
```

ext 里的代码这样调用：

```arm
ldr  r3, [r9, #0x114]     ; 从函数表取出"mr_open 的地址"
blx  r3                   ; 跳过去
```

它以为自己在调用一个函数，实际上**跳到了表项自己所在的地址**。宿主在执行引擎上装一个
"每指令 hook"，PC 落在这些地址上时被拦下来，读写寄存器完成调用，然后 `PC = LR` 模拟 `ret`。

### 3.3 三个关键细节

**① 槽位里必须写它自己的绝对地址**，不是函数指针，不是 0。写错就是跳到别处执行垃圾。

**② 参数传递**：直接从 `r0,r1,r2,r3` 取，第 5 个起从 SP 指向的栈上取。返回值写回 `r0`。

**③ 模拟 ret**：不能真的"返回"，要手动把控制器交回调用者：

```
uc.reg_write(R0, retval)      # 返回值
uc.reg_write(PC, LR)          # 假装执行了 bx lr
```

在 Unicorn 里 hook 回调返回后执行继续，所以这两步做完，下一条指令就是调用者的下一条。

### 3.4 为什么不用"直接给函数地址"

因为 ARM 代码拿到的地址必须指向**真正可执行的代码**。如果你把宿主函数的地址填进去，
执行引擎会直接跳到宿主地址空间跑，那是宿主的机器码，不是 ARM 指令，必然崩。

用"表项自身地址"这个技巧，地址既是有效的 ARM 代码地址（表本身在可执行页里），
又能唯一标识一个槽位。**槽位号 = 地址**，一举两得。

## 4. 两张表：146 + 51 个槽位

ext 需要两组函数：

| 表 | 项数 | 用途 | 基址从哪拿 |
|---|---|---|---|
| `mr_table` | **146** | 全部 `mr_*` 系统 API | 宿主直接写入 `CODE_ADDRESS + 0` |
| `dsm_require_funcs` | **51** | Mythroad 需要的少量回调（含 `_mr_c_function_new`、`mr_extHelper` 等） | 由 `mr_c_function_load` 时通过参数/回调交换 |

（A 级实测：`len(MR_TABLE)==146`、`len(DSM_FUNCS)==51`，且真实 `cfunction.ext` 在此布局下
正常启动。注：早期资料常写 143/52，实际按偏移连续性推导为 146/51。）

### 4.1 表基址怎么交给 ext

宿主直接把基址**写在代码段开头**，ext 启动时从固定偏移读取：

```
CODE_ADDRESS + 0   : mr_table 基址
CODE_ADDRESS + 4   : mr_c_function_P（ext 全局结构指针，启动后回填）
CODE_ADDRESS + 8   : ARM 入口点（宿主从这里开始执行）
```

`+4` 这个位置是**硬约定**：ext 内部的 `fixR9` 系列桩函数靠
`*(mr_c_function_load 地址 - 4)` 找回自己的 `P`。位置错一位，它拿到的就是表基址，
后面所有全局变量访问全废。

（C 级：`vmrp/bridge.c` 与 `mythroad/fixR9.c`；A 级：本项目实测该约定成立。）

---

## 5. r9 静态基址问题（fixR9）

r9 在 ARM EABI 里是 **SB（Static Base）**，指向模块的全局变量区。Mythroad 的 ext 在
`mr_helper()` 入口把 r9 从 r10 恢复成 `P->start_of_ER_RW`（自己的全局数据段）。

问题是斯凯当年的实现有个 bug：ext 调用 mythroad 层 API 时 r9 **没有切回来**，
导致 mythroad 层的全局变量引用全部跑飞。官方修补方式（C 级，`mythroad/fixR9.c` + 
`genR9R10.js` 生成）是给每个 API 套一个汇编桩：

```
asm_xxx:
    push {r0-r12, lr}       ; 保存现场
    bl   fixR9_begin        ; 把 r9/r10 切到 mythroad 层
    bl   real_xxx           ; 调用真函数
    bl   fixR9_end          ; 切回 ext 的基址
    pop  {r0-r12, lr}
    bx   lr
```

### 5.1 模拟器要不要实现这个？

**不用。** 那批汇编桩是 ext 里的**真实 ARM 指令**，在我们的执行引擎里照常执行，
切换在 ARM 侧完全闭环。

模拟器只需要负责两件事：

1. 把 `P` 写进 `CODE_ADDRESS + 4`（见上一节）；
2. 当宿主**主动直跳** ARM 回调（比如网络数据到达）时，手动保存/设置/恢复 r9：

```python
saved = uc.reg_read(R9)
uc.reg_write(R9, P->ER_RW)     # 切到 ext 的全局区
run_code(callback_addr)
uc.reg_write(R9, saved)        # 恢复
```

（A 级实测：对执行期 r9 采样 12318 条指令，r9 恒等于 `P->ER_RW`，零偏差；
helper 返回后 r9 回到 0，属正常的现场恢复。）

### 5.2 唯一需要手动切 r9 的场景

网络异步回调（vmrp 里 `bridge_dsm_network_cb` 是唯一一处碰 r9 的宿主代码）。
本项目对应 `vm.call_arm()`。除此之外宿主不应干预 r9。

## 6. 事件与定时器循环

宿主的主循环负责两件周期性的事：

```python
while running:
    if due(timer_interval_ms):      # 通常 100~300 ms
        vm.timer()                  # → MR_TIMER 事件
    for ev in pending_events:
        vm.event(ev.code, ev.p0, ev.p1)   # → MR_EVENT
    render()                        # 把帧缓冲画到屏幕
    handle_input()                  # 按键/触摸 → vm.key_event / vm.touch_event
```

### 6.1 事件结构

投递时宿主构造一个 12 字节结构写进固定地址（三字：`code, p0, p1`），然后调用 ext 的
事件入口 `mr_extHelper(P, 1, event_addr, 12)`。ext 解析后分派给应用。

### 6.2 定时器语义

- `mr_timerStart(ms)` / `mr_timerStop()` 让应用注册自己的节拍；
- 无论如何 **`MR_TIMER` 事件都要按固定间隔投递**，因为 Mythroad 内部靠它驱动动画、
  光标闪烁、音频队列等；
- 间隔太大会卡（动画跳帧），太小会空转（CPU 100%）。100~300 ms 是可用区间。

### 6.3 事件码速查

见 [01 §3.1](01-三层结构与移植模型.md#31-事件码) 或 [09 常量速查](09-常量速查.md)。

## 7. 图形：直接写帧缓冲

没有任何图形 API 抽象层。应用和 Mythroad 都是**直接往一块 RGB565 连续内存里写像素**：

```
framebuffer: width * height * 2 字节
像素格式:    RGB565（R5 G6 B5，小端）
行跨度:      通常等于 width * 2（可能因平台对齐而更大，用 mr_getScreenInfo 查）
```

`mr_drawBitmap` 只是把一块位图 blit 上去，**不做 alpha、不做缩放**（缩放由应用自己做）。
包内 `.bmp` 就是裸 RGB565 像素数据，没有 `BM` 文件头——这一点在
[03 MRP 包格式](03-MRP包格式规范.md) 里有实测证据。

宿主这一侧要做的：把这块内存包装成一个可直接呈现的 surface（pygame 的 16 位 Surface
正好能吃 RGB565，可以零转换直出）。

## 8. 一次完整调用的时序

以应用调 `mr_open("a.txt", MR_FILE_RDONLY)` 为例：

```
ARM 代码
  ldr r3, [r9, #0x114]    ; 取槽位地址（0x114 是示例偏移）
  mov r0, #0x2A5B74       ; 指向 "a.txt" 的指针
  mov r1, #0              ; MR_FILE_RDONLY
  blx r3                  ; 跳进槽位

执行引擎
  PC == 槽位地址 → 触发 code hook

宿主 hook
  读 r0/r1 → "a.txt", 0
  调 VirtualFs.open("a.txt", 0) → 句柄 1
  写 r0 = 1
  写 PC = LR            ; 模拟返回

ARM 代码继续执行，r0 里就是文件句柄
```

这条链路是本项目自检脚本验证的核心（`tests/selftest.py` 用手写 ARM 机器码直接调槽位）。

## 9. 性能参考

| 项目 | 数据 |
|---|---|
| 执行引擎 | Unicorn 2.x（QEMU TCG 内核） |
| 实测规模 | 启动器完整启动 ≈ 数十万条 ARM 指令，秒级完成 |
| 瓶颈 | 不在 ARM 执行，而在 **API 实现**（尤其文件 I/O 和逐像素操作） |
| 优化点 | ① 内存零拷贝；② blit 用宿主原生 blit 而非逐像素；③ 文件系统加缓存 |

如果想再快：`UC_HOOK_CODE` 覆盖整段代码是主要开销，可以只对函数表所在页装 hook
（表是连续的几 KB，不需要全代码段 hook）。

## 10. 验证方法：怎么证明你的实现真的对

不要靠"看起来能跑"判断。按这个顺序验：

1. **硬编码 ARM 指令调槽位**：手写 `mov r0,#42; blx r3` 调 `mr_getTime`，看 r0 是否合理；
2. **函数表项数**：146 / 51，偏移连续无空洞；
3. **`cfunction.ext` 能否完成初始化**：`mr_dsm_init()` 返回 0，且日志里能看到它调了哪些 API；
4. **能否 `start_dsm` 成功**：返回 0；
5. **画面是否出现**：截图里能看到应用界面（位图 + 文字）；
6. **按键是否响应**：投递按键后画面变化（这条能暴露键值表抄错）。

前 4 步是纯逻辑，第 5、6 步才是"真的跑起来了"。
