# 08 · 陷阱清单

实现 PymRP 过程中实际踩过的坑。每条按 **现象 → 根因 → 正解** 组织，
全部为 A/C 级（实测或双源码交叉验证）。按主题分组。

---

## 一、常量与协议（抄错一个值，整个功能装死）

### 1.1 键值表 ⚠️ 最致命

- **现象**：菜单完全不响应"确定"，但方向键正常。
- **根因**：`MR_KEY_SELECT` 的真值是 **20**，想当然写成 16——而 16 是 `MR_KEY_POWER`
  （挂机键）。每次按确定都在给应用发"挂机"，它当然不理。
- **正解**：键值枚举顺序是 `数字0-9 → * → # → 上→下→左→右 → POWER(16) →
  软左(17) → 软右(18) → SEND(19) → SELECT(20) → CLEAR(23)`。
  以 `mrporting.h` 为唯一依据，不要凭直觉。

### 1.2 事件码

- **现象**：按键时灵时不灵 / 完全不灵。
- **根因**：`MR_KEY_PRESS = 0`、`MR_KEY_RELEASE = 1`（不是 1/2）；
  `MR_MOUSE_DOWN/UP/MOVE = 2/3/12`（不是 3/4/5）。
- **正解**：以 `mythroad/include/mrporting.h` 两个 enum 逐字核对。

### 1.3 `MR_IGNORE = 1`

- **现象**：所有"平台不支持"的分支走错，应用行为怪异。
- **根因**：想当然写成 3。
- **正解**：`#define MR_IGNORE 1`（mrpoid 与 vmrp 两份头文件一致）。

### 1.4 `MR_PLAT_VALUE_BASE` 双重语义

- **现象**：`mr_platEx(209x)` 查播放状态永远判断错。
- **根因**：返回 `1000 + 状态`，而 `1001` 按布尔真值看也"成功"。
- **正解**：先查接口文档确定它是否用 BASE 偏移，再解释数值。
  详见 [01 §2.3](01-三层结构与移植模型.md#23-mr_plat_value_base--最容易踩的语义陷阱)。

### 1.5 `MR_SOUND_TYPE` 两版枚举冲突

- **现象**：WAV 被当 PCM 播，噪声爆炸；或反过来。
- **根因**：老版 5 值枚举（PCM=4）与 vmrp 7 值版（PCM=3）在 3/4 上互换，
  应用按编译时的头文件传值。
- **正解**：不看 type 看数据魔数（`RIFF`/`MThd`/`#!AMR`），见
  [05 §2.2](05-声音与流媒体专题.md#22-type-枚举两版不兼容-⚠️)。

### 1.6 AMR 魔数是 5 字节

- **现象**：AMR 永远识别不出来。
- **根因**：写成 `data[:6] == b"#!AMR\n"`——右边的字节串是 5 字节，6 vs 5 永不相等。
- **正解**：`data[:5] == b"#!AMR\n"`（或 `startswith`）。

## 二、启动链路

### 2.1 直接启动游戏包 → `code=3006`

- **现象**：`start_dsm("box.mrp", "cfunction.ext")` 报 `read file cfunction.ext err code=3006`。
- **根因**：斯凯的包结构要求先跑**启动器**（`dsm_gm.mrp`，入口 `start.mr`），
  由它枚举、下载、加载游戏。游戏包内的 `cfunction.ext` 是另一份 helper，
  不是 331 KB 的主运行时。
- **正解**：先启动 `dsm_gm.mrp`，从菜单选应用。直接 `start_dsm` 游戏包不是支持的用法。

### 2.2 入口名

- **现象**：换个包就启动失败。
- **根因**：`start_dsm` 第二参数是**包内入口文件名**，启动器是 `start.mr`，
  普通应用是 `cfunction.ext`，老应用还有别的名字。
- **正解**：按包名自动判断（`dsm_gm.mrp → start.mr`，其余 → `cfunction.ext`），
  并保留 `--ext` 手动覆盖。

### 2.3 工作目录

- **现象**：启动器菜单空白。
- **根因**：启动器用**相对路径** `mythroad/xxx.mrp` 枚举游戏，workdir 错了就什么都扫不到。
- **正解**：workdir 必须指向包含 `mythroad/` 子目录的那一层。

### 2.4 `CODE_ADDRESS+4` 的约定

- **现象**：ext 里全局变量访问全飞，崩在莫名地址。
- **根因**：`mr_c_function_P` 必须写到 `CODE_ADDRESS+4`——ext 的 fixR9 桩靠
  `*(load_addr - 4)` 找回自己的 P，偏一位就拿不到。
- **正解**：三个地址是硬约定：`+0` 表基址、`+4` P 指针、`+8` ARM 入口。

### 2.5 函数表槽位内容

- **现象**：一调用就跳到奇怪地址执行垃圾。
- **根因**：槽位里写的是宿主函数地址（宿主的机器码不是 ARM）或 0。
- **正解**：**每个槽位写它自己的绝对地址**，用 code hook 拦截。
  见 [02 §3](02-运行原理-虚拟机怎么跑MRP.md#3-核心机制用内存地址当-syscall-号)。

## 三、执行引擎（Unicorn）

### 3.1 `mem_read/mem_write` 性能

- **现象**：帧率低到幻灯片。
- **根因**：每次 API 调用都跨语言拷贝内存，逐像素操作放大上百万次。
- **正解**：**零拷贝**——`mem_map` 后保留宿主侧 buffer 引用直接读写；
  blit 用宿主原生能力一次完成。

### 3.2 hook 范围

- **现象**：整体慢 2~5 倍。
- **根因**：`UC_HOOK_CODE` 挂满整个代码段，每条指令都进回调。
- **正解**：只对**函数表所在的几 KB** 装 hook（表是连续区域）。

### 3.3 runCode 的停止地址

- **现象**：执行"飞了"或提前停止。
- **根因**：`emu_start(begin, stop)` 的 stop 同时被写进 LR 当"返回地址"。
- **正解**：所有宿主发起的执行统一 `LR = stop = CODE_ADDRESS`，
  并保证该地址不会被执行到第二次（或接受它作为哨兵）。

### 3.4 r9 不需要模拟器维护（除一处）

- **结论**：fixR9 桩是 ext 里的真实 ARM 指令，切换在 ARM 侧闭环（实测 12318 条指令
  r9 恒等于 `P->ER_RW`，零偏差）。宿主只做两件事：写对 `+4` 的 P；
  **宿主主动直跳 ARM 回调**时 save/set/restore r9（对应 vmrp 的 network_cb）。

### 3.5 `MAP_DATA` 槽位存的是值

- **现象**：`mr_soundOn` 读出来是地址，应用静音。
- **根因**：把数据槽当成"存指针的槽"。实际上 MAP_DATA 槽位**直接存值本身**
  （vmrp `hooks_init` 对无 initFn 的数据槽不做任何处理）。
- **正解**：`mr_screenBuf` 这类"要指针"的槽例外——初始化时由 initFn 填地址；
  其余数据槽一律填值。

### 3.6 低地址野指针会终止整个 VM ⭐

- **现象**：曲奇启动器 `PC=0x87A24` 读 `@0x15858(2B)` → `UC_ERR_READ_UNMAPPED`，
  `timer` 异常后整个模拟器退出。
- **根因**：真 MTK 机器 `0x0` 往上到代码段起点都是固件 ROM / 低地址 RAM，
  可读；透明位图 blit 拿到垃圾源指针时只是读到 0，不会终止。
  我们只映射了 `0x0–0x10000` 零页，`0x15858` 落在空洞里。
- **迷惑点**：先怀疑是 r9/SB 切换（反汇编里 `ldr lr,[pc,#…]; add lr,lr,sb`），
  实测崩溃时 `r9=0x2A5B74` 正常，排除。
- **正解**：`vm.py` 把低地址映射扩到 `LOW_MEMORY_SIZE = CODE_ADDRESS`，
  整段零填充。只补到 `0x20000` 不够——崩溃只会从第 0 帧推迟到第 5 帧。
- **取舍**：这会容忍一部分真野指针（读到 0 而非崩），复古兼容优先；
  诊断靠 `UC_HOOK_MEM_INVALID` 日志。详见 [15 §二](15-曲奇启动器崩溃复盘.md#二崩溃点反汇编铁证a-级)。

## 四、包格式与资源

### 4.1 包内 bmp 没有 BM 头

- **现象**：拿 BMP 解析器去解包内图片，直接失败。
- **正解**：包内 `.bmp` 是**裸 RGB565 像素流**，宽高要么全屏要么应用硬编码。
  见 [03 §4](03-MRP包格式规范.md#4-数据区)。

### 4.2 gzip 解压参数

- **现象**：`zlib.error: incorrect header check`。
- **根因**：gzip 流不是 raw deflate。
- **正解**：`zlib.decompress(data, 16 + zlib.MAX_WBITS)`。

### 4.3 图标位图宽度不是 240

- **现象**：以 240 为宽计算图标尺寸，花屏。
- **正解**：宽度由应用自己约定（实测见过 32×56 的列表图标），
  宽高信息不在文件里。

### 4.4 DSM 局部刷屏用错 stride（重复标题栏 + 蓝色斜纹）⭐

- **现象**：RX 管理器静止首帧正常，一滚动列表/弹菜单就出现**重复标题栏**
  和**蓝色横条里夹斜向噪点**；某些帧又自动恢复。看截图会误判成"字库损坏"
  或"图层合成失败"。
- **根因**：`dsm_require_funcs.drawBitmap` 被当成 `mr_table.mr_drawBitmap`
  复用。前者的 `bmp` 是**整屏离屏缓冲基址**、源行跨度是屏宽 240、`x/y`
  是源矩形左上角；后者才是一块紧凑 `w × h` 位图。按 `w` 跨度读，等于
  每次都把屏顶标题栏贴到目标行。见 [06 §1.3](06-图形与图层专题.md#13-同名陷阱两条-drawbitmap-路径的-stride-不同a-级源码--实测)。
- **迷惑点**：整屏刷新 `(0,0,240,320)` 时 `w == 屏宽`，两种语义等价，
  所以只有局部脏矩形会出错；另外两个缓冲地址不同（实测 `0x280000` vs
  `0x2A8180`），光看"屏幕内存"找不出问题。
- **正解**：单独实现 `dsm_drawBitmap` → `Gfx.refresh_rect()`，
  按 `src[sw*i + x]` 取源、写回帧缓冲同位置；`ALIAS` 里两条路径分开绑定。
- **验证**：`tests/gfx_probe.py`（21 项）+ `tests/rx_gfx_trace.py`（调用参数
  与离屏缓冲导出）。从 pyz 复测同样正常（`PYMRP_FROM_PYZ=1`）。

### 4.5 半个汉字 + 长中文文件名 = 资源全缺 ⭐

- **现象**：日志出现 `mythroad/Ã°ÅÝ6.0…`（乱码且末尾被截断），
  `read "res_lang0.rc" from mrp err,code=2002`，应用停在深蓝空屏。
- **两个独立原因**：
  1. ext 用固定小缓冲（曲奇实测 41 字节）拼路径，长中文名被截断在**半个汉字**上；
     `cstr()` 的 `gbk → utf-8 → latin-1` 兜底遇到不完整 GBK 就整串按 latin-1 解，
     `C3 B0 C5 DD`（冒泡）变 `Ã°ÅÝ`。**字节本身是干净 GBK，不是 ext 造的乱码**。
  2. 即便不乱码，被截断的路径也打不开，`mr_open(pack_filename)` 失败即 `code=2002`
     （C 级，`mythroad/mr_file.c`）。`code=1001` 是 `*A`/`$` 内存包指针为 NULL。
- **正解**：`cstr()` 改 GBK 宽容解码；`catalog.safe_run_name()` 用包头 `0x10`
  的 8.3 ASCII 短名（曲奇是 `cookie.mrp`）作为运行名，短名原样不动。
  见 [15 §三、§四](15-曲奇启动器崩溃复盘.md)。
- **验证**：`tests/cookie_probe.py`（35 项），真实曲奇 300 帧零异常、
  帧缓冲 72690/76800 非零、日志乱码 0 条、`res_lang0` 2002 归零。

## 五、宿主环境（Windows / Python）

### 5.1 `pygame.font.match_font` 注册表崩溃

- **现象**：`int` 解析注册表值出错，pygame 字体全挂。
- **正解**：不用 `match_font`/`SysFont`，直接探测字体文件路径
  （`C:\Windows\Fonts\xxx.ttf`）建缓存。

### 5.2 `python -c` 不加 cwd 进 `sys.path`

- **现象**：`import mrp_emu` 失败，同目录下明明有包。
- **根因**：环境开启了 `PYTHONSAFEPATH`（`sys.flags.safe_path=1`）。
- **正解**：统一用显式入口脚本（`run.py`），内部把自身目录插进 `sys.path`。

### 5.3 pyz 里 `__file__` 不可用

- **现象**：打包成 pyz 后找不到 runtime / 资源目录。
- **正解**：用 `sys.argv[0]` 推程序目录；资源文件（runtime 等）**不打进 pyz**，
  从程序目录或 cwd 找。

### 5.4 vmrp 发行 zip 的同名条目

- **现象**：解压报错或文件被目录项覆盖。
- **根因**：zip 里 `mythroad` 同时存在文件条目和目录条目（Windows 打包怪癖）。
- **正解**：解压循环里对"目录自身条目"和"名字冲突"做防御。

### 5.5 `pygame.init()` 让启动卡 8 秒 ⭐

- **现象**：Windows 无音频端点的机器上，从 pygame 欢迎日志到界面出来要 20 秒
  （实测端到端 17.12s）。
- **根因**：`pygame.init()` 连带 `SDL_INIT_AUDIO`，SDL 2.28 的 WASAPI 驱动
  枚举设备超时 **8.1s**；`AudioEngine` 启动时同步调 `pygame.mixer.init()`
  又花 **8.0s** 且最终还是失败降级成静音。
- **迷惑点**：headless / dummy 音频驱动下全套启动只要 0.9s，很容易误判成
  字体加载或在线索引加载慢。逐段计时才能看到两次 8 秒。
- **错误尝试**：把 `mixer.init()` 丢后台线程——界面虽早出，但 WASAPI 的 C
  调用不释放 GIL，主循环 90 帧从 1.5s 被拖到 9.5s，反而更卡。
- **正解**：`cli.py::init_pygame_minimal()` 只做 `display.init()+font.init()`
  （~6ms）；`audio/mixer.py::_device_probe()` 用 winmm 的
  `waveOutGetNumDevs()`（0.023ms）判定无设备就直接静音，不碰 SDL 音频。
  详见 [17](17-启动性能：SDL初始化与音频设备探测.md)。

### 5.6 用真实运行目录做确定性回归 ⭐

- **现象**：`gfx_probe` / `net_probe` 的「RX 管理器 90 步按键」偶发
  `UC_ERR_READ_UNMAPPED`，用 HEAD 原版代码复跑同样失败。
- **根因**：RX 等应用运行时会在 `mythroad/` 下自建 `brw/`、`cookie/`、
  `app240320/`、`*.sid` 缓存目录。下一次跑时目录枚举结果变了，固定按键
  序列走进新分支，崩在应用自身的目录项野指针（`PC=0x2E26AE` 读
  `0xF82D4AE8`）。**上一次的输出成了这一次的输入**。
- **正解**：`tests/rx_env.py` 构造隔离快照，只复制 `cfunction.ext` +
  `mythroad/*.mrp`，不带任何应用缓存目录；探针跑完 `cleanup()`。
  凡涉及文件系统遍历的用例都必须用隔离环境。

### 5.7 高分屏下界面发虚 ⭐

- **现象**：窗口开了缩放（或 Windows 显示缩放 125%/150%）后，整机界面像被
  拍扁的贴图，文字笔画糊成一片。
- **两个独立原因**：
  1. 进程不感知 DPI → Windows 把窗口当位图拉伸一次；
  2. 我们自己再 `smoothscale` 拉伸一次成品图 → 非整数倍缩放必然糊。
- **正解**：`cli.py::enable_dpi_awareness()` 设 `PER_MONITOR_AWARE_V2`
  （必须早于 `set_mode`）；机壳改成**整数倍矢量重绘**
  （`skin.py::scaled_skin` + `PhoneUI(scale=k)`），不再拉伸成品图。
- **教训**：非整数倍缩放无解 —— 像素会被打散到半个物理像素上，插值柔、
  最近邻糙。详见 [18 §一](18-高分屏缩放与退出收尾.md#一缩放为什么糊两个独立的放大)。

### 5.8 `vm.exited` 只设不读，退出后一片狼藉 ⭐

- **现象**：应用调用 `mr_exit()` 后，背景音乐还在响、网络还挂着、文件句柄
  还占着、界面回不到系统界面。
- **根因**：`mr_exit()` 只做 `vm.exited = True`，而**没有任何人消费这个标志**。
- **正解**：`App.shutdown_session()` 统一收尾（停声音 / 关 socket / 关句柄），
  `cli` 主循环每帧检查 `vm.exited` → 收尾 → `back_to_home()`。
  另外所有虚拟机调用（`key_event` / `touch_event` / `timer`）要包一层
  `guarded`，否则 MRP 野指针崩了会直接带走整个模拟器进程。
  详见 [18 §二、§三](18-高分屏缩放与退出收尾.md)。

## 六、应用行为（不是你的 bug）

### 6.1 点屏幕没反应

- **结论**：这批应用是按键驱动，不处理 `MR_MOUSE_*`。事件已正确送达（可用内存探针验证），
  应用自己不处理。见 [00 §3.2](00-这套系统是什么.md#32-按键不是触摸)。

### 6.2 `mr_soundOn` 全局静音

- **结论**：mythroad 层有全局声音开关，为 0 时应用侧 `mrc_playSound` 直接短路
  （C 级，mythroad.c）。排查声音问题先查它。

### 6.3 不少游戏就是没有声音

- **结论**：推箱子等老游戏包里就没有音频资源（或只在特定场景触发）。
  排查时先 `mrp_pack.py list` 看包内有没有 `.mid`/`.wav`。

### 6.4 `MR_IGNORE` vs `MR_FAILED`

- **结论**：应用对 `MR_IGNORE` 的预期是"降级到旧路径"，对 `MR_FAILED` 的预期是
  "出错"。未实现的扩展接口返回 `MR_IGNORE` 通常更安全。

## 七、记住这三条元规律

1. **一切以头文件为准**：`mrporting.h`、`dsm.h`、`vmrp.h`——手册会含糊，直觉会骗人，
   枚举值不会。
2. **斯凯的体系是"约定"不是"协议"**：`+4` 的 P、槽位自指、相对路径枚举……
   都没有文档，只能从源码和实测反推。所以[资料溯源](10-资料溯源与考古.md)很重要。
3. **每个修复都要配一个探针测试**：键值表抄错这种事发生过一次，就会发生第二次。
   `tests/key_probe.py` 的 17 项断言就是为此存在的。
