## 一、结论先行

这不是一个 bug，是**四个独立问题叠在一起**，其中三个属于模拟器、一个属于运行环境：

| # | 问题 | 归属 | 后果 |
|---|---|---|---|
| 1 | 低地址 `0x0–0x80000` 只映射了 `0x0–0x10000` | 模拟器 | 透明位图 blit 读到 `0x15858` → `UcError` **终止整个 VM** |
| 2 | `cstr()` 的 `gbk → utf-8 → latin-1` 兜底 | 模拟器 | 路径被截断在半个汉字上时，整串退化成 latin-1，`冒泡` 变 `Ã°ÅÝ` |

## 二、崩溃点：反汇编铁证（A 级）

`cfunction.ext` 加载到 `0x80000`，故 `PC=0x87A24` 对应文件偏移 `0x7A24`。
用 capstone 按 **ARM 模式**反汇编（不是 Thumb，指令能完美对齐）：

```asm
0x0879E0: ldr    lr, [pc, #0x2c4]
0x0879E8: add    lr, lr, sb            ; sb = r9 静态基址
0x0879EC: ldr    r0, [lr, #0x40]
0x0879F4: ldr    r0, [lr, #0x3c]
0x0879FC: add    r0, r0, r1, lsl #1
0x087A00: add    r1, r0, r4, lsl #1
0x087A18: add    lr, r0, fp, lsl #1    ; lr = 源位图指针
0x087A24: ldrh   sl, [lr]              ; ★ 读 2 字节像素，崩在这里
0x087A30: cmp    sl, r3               ; 透明色比较
0x087A34: strhne sl, [r1]             ; 非透明才写目标
0x087A38: add    r1, r1, #2
0x087A40: add    lr, lr, #2
0x087A44: blt    0x87A24              ; 逐像素透明 blit 循环
```

非法访问 `@0x15858(2B)` 与 `ldrh` 的 2 字节读完全吻合（A 级）。
`0x15858` 不在我们任何映射区里：`mem_map_ptr` 只覆盖 `0x80000–0x880000`，
零页只覆盖 `0x0–0x10000`。

**寄存器实测**：崩溃时 `r9 = 0x2A5B74`（正常堆地址），
所以**不是 r9/SB 切换问题** —— 排查时先排除掉了这条老坑。

### 为什么真机不崩

真 MTK 机器从 0 地址往上直到代码段起点都是固件 ROM / 低地址 RAM，可读；
老应用拿到野指针时读到 0（或 ROM 内容），blit 顶多画出一堆透明/黑像素，
不会终止进程。Unicorn 默认不映射 0 页，我们把"未映射"直接抛成致命异常，
才把整个 VM 带崩。

**修复**（`mrp_emu/vm.py`）：把低地址映射从 `ZERO_PAGE_SIZE = 0x10000`
扩到 `LOW_MEMORY_SIZE = CODE_ADDRESS = 0x80000`，整段零填充、可读可写。

> 取舍：这会容忍一部分真正的野指针解引用（读到 0 而不是崩），
> 是复古兼容优先的决定。诊断能力靠 `UC_HOOK_MEM_INVALID` 日志保留。

**敏感性对照**（`tests/cookie_probe.py`）：只补 `0x10000–0x20000` 时崩溃
从第 0 帧推迟到第 5 帧；补满 `0x80000` 后 300/300 帧零异常。

## 三、GBK 字符串：乱码不是 ext 造的（A 级）

日志里出现过一条诡异路径：

```
[fs] 打开失败 mythroad/Ã°ÅÝ6.0£¨ÏßÌõÄ£ÄâÆ÷ÌáÈ¡£¨ÇúÆæÆô¶
```

初看像是 ext 内部编码转换出错。做字节级诊断（`MrpMemory.cstr` 打点）后，
**ext 传给 `mr_open` 的原始字节其实是干净的 GBK**：

```
6d 79 74 68 72 6f 61 64 2f c3 b0 c5 dd 36 2e 30 a3 a8 ...
mythroad/  冒   泡   6 . 0  （   ...
```

只不过被 ext 自己的固定缓冲**截断在半个汉字上**（41 字节，末尾 `...f4 b6`）。
老 `cstr()` 是这么写的：

```python
for enc in ("gbk", "utf-8"):
    try:
        return raw.decode(enc)
    except UnicodeDecodeError:
        continue
return raw.decode("latin-1")     # ← 元凶
```

不完整 GBK 序列让 `gbk` 严格解码抛异常，`utf-8` 也失败，
最后整串按 latin-1 解 → `C3 B0 C5 DD` = `Ã°ÅÝ`。

**修复**（`mrp_emu/memory.py`）：MRP 世界的字符串就是 GBK/ASCII，
改成 GBK 宽容解码 `errors="replace"` + 丢替换符；
只在替换符 ≥2 且严格 UTF-8 解码成功时才认定是 UTF-8。
修完 `Ã°ÅÝ` 从日志里彻底消失，路径变成正确的
`mythroad/冒泡6.0（线条模拟器提取（曲奇启`（虽仍被截断）。

## 四、长中文文件名：ext 的 32 字节路径缓冲（A 级）

即便路径不再乱码，被截断的名字仍然打不开：

```
[fs] 打开失败 mythroad/冒泡6.0（线条模拟器提取（曲奇启
[arm] read "res_lang0.rc" from mrp err,code=2002
```

`res_lang0.rc` **就在曲奇包内**（条目 77，4725 字节），
只是 ext 拿截断后的路径去 `mr_open(pack_filename)`，自然失败。

`code=2002` 的语义在 mrpoid `mythroad/mr_file.c` 里写得很清楚（C 级）：

```c
fd = mr_open(pack_filename, MR_FILE_RDONLY);
if (fd == 0) { _mr_readFileShowInfo(filename, 2002); return NULL; }
```

`code=1001` 是另一条分支：`pack_filename` 为 `*A`/`$` 的内存包，
但 `mr_m0_file`/`mr_ram_file` 为 NULL（`mr/mythroad.c:2955`）。
两者都表示**资源容器没挂上**，不是字库或图层问题。

### 真机上这个应用叫什么

读 MRP 固定头 `0x10`（`filename` 字段）：

| 字段 | 值 |
|---|---|
| `filename@0x10` | `cookie.mrp` |
| `title@0x1C` | `冒泡6.0（曲奇启动）` |
| `vendor@0x58` | `sky` |
| 条目数 | 145（`start.mr`、`mrc_loader.ext`、`game.ext`、`logo.ext`、大量 `*.bmp` / `*.itm`） |

真机上它就叫 `cookie.mrp`，8.3 ASCII 短名，根本不会触发截断。
老板给的中文长名是整理文件时重命名的结果。

**修复**（`mrp_emu/catalog.py::safe_run_name` + `cli.py::ensure_in_mythroad`）：
启动前自动把长名/中文名换成包头声明的短名（回退时用文件名散列），
复制进 `mythroad/` 并用短名 `start_dsm()`；窗口标题仍显示原中文名。
短 ASCII 名（`dsm_gm.mrp`、`box.mrp`…）原样不动，零回归。

**隔离实验**：

| 状态 | 结果 |
|---|---|
| 仅补低地址映射 | 不崩，但停在错误框 `, (103) !` |
| + GBK 容错 | 不崩、无乱码，但仍是**深蓝空屏**（`res_lang0.rc` 2002） |
| + 自动短名 | **完整九宫格主界面**，帧缓冲非零像素 72690/76800 |

## 五、顺带修正：`c2u` 槽位（C 级源码 + A 级单测）

`mr_table` 槽位 1939 的官方签名（`mr/mr_gb2312.c:609`、`mr/mythroad.c:589`）：

```c
typedef unsigned short unicode_char;
unicode_char *c2u(const char *cp, int *err, int *size);
```

- 返回**新分配**的 `uint16` 数组，调用方负责 `MR_FREE`；
- `*size` 是字节数 `(字符数+1)*2`；
- 小端机上源码手工交换了高低字节，所以**内存布局是 UTF-16BE**；
- `err` 传入时开头被写成 `-1`，成功不改回。

旧实现把 arg1 当目标缓冲、写 UTF-8 字节、并返回 arg1 —— 三个参数全错。
曲奇实测**没有调用**这个槽位（打点计数 0），所以不是本次崩溃的原因，
但其它调用该 API 的 MRP 会拿到野指针。已按官方语义重写，并加了
`tests/cookie_probe.py` 的 6 项断言（UTF-16BE 字节、size、err、可释放性）。

## 七、遗留：仍缺的运行时资源（不是模拟器的 bug）

修完后日志里仍会打这些 `[fs] 打开失败`，属**外部环境**，主界面不受影响：

```
mythroad/app240320/0/resmrp.mrp          # 资源容器包
mythroad/app240320/res/5KU.bmp … 5LL.bmp # 9 个短名图标缓存
mythroad/app240320/sgm/rollmsg.dat       # 滚动消息
mythroad/app240320/cfg/localdir.sav      # 目录配置（应用会自己写）
mythroad/disk/b/system/monlimit.sav
mythroad/plugins/netpay.mrp
mythroad/gsidbak/gsidbak.mrp.sid
```

- `app240320` / `plugin240320` 是 240×320 分辨率的**斯凯运行时资源目录**，
  真机上由手机预置或首次联网下发；`5KU`、`663` 这类三字符短名是资源 ID 缓存，
  不在任何本地 MRP 的条目表里（已扫描 runtime 下 27 个包，0 命中）。
- `read "5ku.bm" from mrp err,code=1001` 里的 6 字符名是 ext 的短名查表形式，
  与文件系统路径 `5KU.bmp` 是同一次资源加载的两条回退路径。
- `ref/skyengine-v2/test/fixtures/mythroad/` 里有 `app240320/cfg/localdir.sav`
  和 `6110cookie.inf` 的测试夹具，但**没有** `res/` 图标与 `resmrp.mrp`。
- 斯凯服务器已停运，这些资源无法再从官方渠道同步，参见
  [14 · 斯凯服务器复活](14-斯凯服务器复活：DNS覆写与WAP代理.md)。
  若老板手上有真机导出的 `app240320/` 资源包，直接放进
  `runtime/mythroad/app240320/` 即可补齐图标。

**边界**：低地址映射会容忍一部分野指针解引用；`c2u` 返回块由调用方释放，
若某个应用只调不释放会累积堆占用（目前 11 套探针未见泄漏）。
