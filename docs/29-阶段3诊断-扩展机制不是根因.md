# 阶段 3 诊断：斯凯扩展机制不是根因，崩在更早的地方

> 老板指示「做」斯凯扩展机制。结果：**做了，但发现它不是当前崩溃的根因**。
> 本文记录这一轮的排除过程 —— 每一个假设都用数据否掉了。

---

## 一、做了什么

1. **注册了 `c_load` / `_mr_c_load` 两个 Lua 全局**（`tools/patch_mythroad.py`）
   —— 它们在 mrpoid 里根本没有注册，是宿主（平台）提供的。
2. 两种实现可切换：
   * `MRP_C_LOAD_STUB=1`（当前默认）：桩，记录调用后返回 nil
   * 真实现：调平台接口 `mr_c_function_load`（`mythroad.h:264`）
3. 加了**崩溃现场快照**（`--trace`）：崩溃瞬间的执行路径 + 崩溃处的指令字节

---

## 二、关键结论：桩**一次都没被调用**

```
崩溃瞬间的执行路径（最后 30 个 PC）：
   0x009DDEE4  0x009DDEE8  ...  0x009DDF58   ← 全部连续落在 mythroad 的堆里
崩溃处指令 @0x9DDF58: a9922af0 07000000 666f7265616368 0090e09d ...
                                  ^^^^^^^^ "foreach"   ^^^^^ "xy"
```

* 崩溃处的内存里是 **`"foreach"`、`"xy"`** —— 这是 **Lua 的字符串常量表**，
  被当成 ARM 指令执行了
* 也就是说：**解释器把一个字符串常量的地址当成函数地址去调用**

### 这排除了什么

| 假设 | 结论 |
|---|---|
| 应用调 `c_load` 失败导致崩溃 | ❌ **桩没被调用**，崩溃在它之前 |
| 字节码容器布局错位 | ❌ 三个应用解析后**结束偏移 == 文件大小**，100% 匹配 |
| number 常量宽度错 | ✅ **已修**（float 补丁，见 docs/28） |
| opcode 编号不匹配 | ❌ 全部落在 `[0,42)` 合法范围，且分布里出现 `36=OP_BAND`（位运算扩展），说明**斯凯基于 mrpoid 定制，编号一致** |
| GETGLOBAL 的 Bx 位布局不对 | ❌ mrpoid 布局(`POS_B=15`) 与标准 Lua 布局(`POS_B=14`) 解出的全局名**完全一致**：`TestCom`/`_platEx`/`_strCom`/`print`/**`c_load`**/`_textWidth` —— 全是合理符号 |
| 操作数位布局整体不对 | ❌ **用寄存器号范围做判据**：`OP_MOVE` 的 A/B 必须是寄存器号(0-31)。dsm_gm 有 205 条 OP_MOVE —— mrpoid 布局(`A@24,B@15`) **0 条越界、最大操作数 17**；标准 Lua 布局(`A@6,B@14`) **5 条越界、最大 34**。**布局与我们的解释器一致** ✅ |

> 顺带确认：**dsm_gm 确实会调 `c_load`**（它的 GETGLOBAL 序列里明确有）。
> 所以扩展机制终究要实现，只是不是当前这一处崩溃的原因。

## 三、方向修正：下一步该验证「解释器 vs 应用字节码」的匹配

到目前为止，**所有能在 Python 侧静态验证的层面都验证通过了**：
容器布局 ✅、number 宽度 ✅（已修）、opcode 编号 ✅、GETGLOBAL 位布局 ✅。

剩下的只能是**执行期语义**层面：某个 opcode 的操作数含义、RK 编码、
或 upvalue/closure 结构，与 mrpoid 解释器的期望有偏差。

> ⚠️ 补充说明：Python 侧解析器验证「结束偏移 == 文件大小」只证明了**字节数**对得上，
> 不证明**字段顺序**对得上。但由于按 mrpoid 顺序解析出的常量表**全是可读字符串**
> （`dofile`/`common.mr`/`QQsid`/`ShowQQmainlist`…），而按别的顺序解析会立刻乱码，
> **字段顺序也可以判定为 mrpoid 的** ✅

### 决定性实验（下一步）

**用 mrpoid 自己的编译器产出的字节码来跑**：

1. `ref/mrpoid/mr/mr_maketo.c` + `mr_formaketo.h` 是 mrpoid 的**编译器**
   （输出 `.mr`）。它是 PC 程序，可以直接在 Windows 上编。
2. 用它编译一个测试脚本 → 得到 **mrpoid 原生格式** 的 `.mr`
3. 把它喂给我们的 VM 跑

| 结果 | 结论 |
|---|---|
| mrpoid 编译的 .mr 能跑 | 解释器没问题 → **斯凯的字节码与 mrpoid 有细微语义差异**，需要逐 opcode 对比 |
| mrpoid 编译的 .mr 也崩 | 我们的移植还有别的问题（解释器/链接/ABI） |

这个实验能把「解释器有 bug」和「应用字节码不兼容」彻底分开。

> ⚠️ 现状修正：**mrpoid 的编译器本体（luac）不在这个仓库里** ——
> `ref/mrpoid/mr/mr_maketo.c` 只是 Lua binding 层（`to_mr_mythroad_open`），
> `tomr/` 也是 binding。所以这个实验暂时做不了。

### 替代方案（下一步的建议）

**从斯凯的 `cfunction.ext` 反推它的 opcode 表**。老架构本来就在 Unicorn 里跑
`cfunction.ext`（它能跑通这些应用），所以：

1. 在老 VM 里跑同一个应用，记录 `cfunction.ext` 解释器的**执行路径**
2. 找出它的 **opcode 分发表**（PC 序列的跳转模式）
3. 反推斯凯的 opcode 编号与操作数布局
4. 与 mrpoid 的表逐项对比 → 定位差异

这条路的好处是**直接拿斯凯的真实实现当基准**，而不是猜。

| 现象 | 根因 |
|---|---|
| `invalid storage class for function 'MRF_c_load'` | 补丁把函数定义插进了 `_mr_intra_start` **函数体内部** → 改插到文件作用域（`#include "mrporting.h"` 之后） |
