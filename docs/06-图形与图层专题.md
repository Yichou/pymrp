# 06 · 图形与图层专题

MRP 的显示分**三层能力**：人人都要用的帧缓冲直写、MTK 平台才有的硬件图层合成、
以及平台侧的图片解码加速。这篇按从底到顶讲清楚。

---

## 1. 基础层：RGB565 帧缓冲直写

整个系统没有"窗口管理器"，应用拿到的就是一块像素内存：

```
分辨率:  常见 240×320（QVGA 竖屏），包格式里 0x0C 处写死
格式:    RGB565（R5 G6 B5，小端 uint16）
跨度:    行 = width × 2 字节
来源:    应用通过 mr_drawBitmap 画图、mr_getCharBitmap 取字模自己绘字
```

### 1.1 核心三件套

| 接口 | 作用 | 备注 |
|---|---|---|
| `mr_getScreenInfo` | 查询宽/高/位深 | 应用初始化第一件事 |
| `mr_drawBitmap` | blit 一块 RGB565 到帧缓冲 | 无 alpha、无缩放 |
| `mr_getCharBitmap` | 取单字字模 | 应用想自己排版文字时用（否则用 mythroad 内置字库） |

### 1.2 包内位图格式

`.mrp` 包里的 `.bmp` **不是 Windows BMP**，是裸 RGB565 像素流（A 级实测，
见 [03 §4](03-MRP包格式规范.md#4-数据区)）。宽高信息不在文件里，
要么是全屏图（宽 = 包头 0x0C），要么由应用硬编码。

所以**模拟器不需要 BMP 解析器**，直接把解压后的字节当像素数组用即可。

### 1.3 同名陷阱：两条 `drawBitmap` 路径的 stride 不同（A 级，源码 + 实测）

这是本项目**最容易误判、又最不容易自查**的一个坑：名字相同、参数签名相同，
但 `bmp` 的含义完全不同。2026-11-10 修 RX 管理器花屏时从 mrpoid 源码反推出来。

| | `mr_table.mr_drawBitmap` | `dsm_require_funcs.drawBitmap` |
|---|---|---|
| 调用方 | 应用 / mythroad 自己贴图片 | DSM 层把 UI **刷到屏幕** |
| `bmp` 含义 | 一块紧凑 `w × h` 位图的首地址 | **整屏 240×320 缓冲的基址** |
| 源行跨度 | `w` 像素 | **屏宽 `sw` 像素** |
| `x/y` 含义 | 只决定**目标位置** | 同时是**源矩形起点**和目标位置 |
| mrpoid 出口 | `emulator.c::emu_drawBitmap` | `dsm.c::mr_drawBitmap` → `emulator.c::emu_bitmapToscreen` |

源码铁证（`mrpoid2018-master/libm/src/main/jni/src/`）：

```c
/* emulator.c:808  emu_drawBitmap —— 紧凑位图，stride = w */
for (r = 0; r < dh; r++)
    memcpy((p + (sw * (y+r)) + x), (data + (w * r)), dw * 2);

/* emulator.c:737  emu_bitmapToscreen —— 全屏缓冲，stride = sw */
for (i = y; i <= y1; i++)
    memcpy((p + (sw * i) + x), (data + (sw * i) + x), w * 2);

/* dsm.c:1436 */
void mr_drawBitmap(uint16* bmp, int16 x, int16 y, uint16 w, uint16 h)
{ emu_bitmapToscreen(bmp, x, y, w, h); }

/* mr/mythroad.c:3842  _DispUpEx */
mr_drawBitmap(mr_screenBuf, x, y, (uint16)w, (uint16)h);
```

**为什么整屏时看不出错**：`(x,y,w,h) = (0,0,240,320)` 时 `w == sw`，
两种 stride 恰好相等，画面完全正常。只有列表滚动、菜单弹出这类**局部脏矩形
刷新**（例如 `(3, 61, 226, 26)`）才会暴露。

**误用后的画面**（RX 管理器实测，见 `out/rx_gfx_before_after.png`）：
局部刷新从离屏缓冲的 `(0,0)` 开始按 `w=226` 连续读，于是把**屏顶标题栏**
贴到 `y=61/90/119/177` 的列表行上 —— 重复三条「RX管理器」标题栏、蓝色
横条里夹着斜向噪点，但静止首帧和整屏刷新后又恢复正常，非常有迷惑性。

**实测数据**（`tests/rx_gfx_trace.py`，90 步真实按键）：

```
gfx.fb_addr = 0x280000       宿主帧缓冲（mr_screenBuf 槽位）
dsm_buf     = 0x2A8180       DSM 离屏全屏缓冲（104 次调用，地址恒定）
drawBitmap 共 104 次：      16 次整屏 (0,0,240,320)，88 次局部矩形
典型局部参数：              (3,61,226,26) (3,90,226,26) (0,254,240,40)
```

**正确实现**（`gfx.py::Gfx.refresh_rect`）：按 `sw` 取源，逐行把
`src[y0:y1, x0:x1]` 写到帧缓冲**同位置**，矩形外不动；负坐标按
`clip_rect()` 钳到 0；源就是 `fb_addr` 时视为已同步直接返回；源缓冲不足
整屏时才退化成紧凑位图语义（兼容个别 DSM 变体）。

> 回归保护：`tests/gfx_probe.py` 21 项，其中「紧凑 blit 用在此处确实会错位」
> 是**敏感性对照**（防止用例退化成永远通过），真实 RX 运行期间对每一次
> drawBitmap 后的 fb 与离屏缓冲做逐像素比对（104 次全一致）。
> 两条路径的绑定在 `api/dsmfuncs.py::ALIAS` 分开，不许再复用同一个实现。

## 2. 进阶层：MTK 图层系统

MTK 芯片的 GUI 有一套**硬件图层**（base 层 + 若干 overlay 层），SkyEngine 把它
暴露出来做半透明 UI、动画等效果。**这是平台相关扩展，不可假设存在**
（返回 `MR_IGNORE` 时应用会退回纯软件方案）。

### 2.1 接口组

| code | 功能 | 备注 |
|---|---|---|
| `mr_platEx(1309)` | 创建层 | 返回层句柄，0 是非法句柄 |
| `mr_platEx(1311)` | 获得 base 层句柄 | base 层就是帧缓冲 |
| `mr_plat(1310)` | 释放层 | |
| `mr_plat(1312)` | 设置激活层 | 后续透明/位置等操作针对激活层 |
| `mr_platEx(1313)` | 设置层位置 | |
| `mr_platEx(1315)` | 获取激活层信息 | |
| `mr_platEx(1316)` | 层叠加 | 合成两层 |
| `mr_platEx(1308)` | 设置参与刷新的层 | |
| `mr_plat(1317/1318)` | 设置/关闭层透明值 | 全局 alpha |
| `mr_plat(1319/1320)` | 设置/关闭层透明色 | color key |

### 2.2 创建层的参数结构（B 级，手册原文）

```c
typedef struct {
    int32 x;
    int32 y;
    int32 w;
    int32 h;
    int32 size;        // buffer 大小
    char *buffer;      // 像素数据（RGB565）
} T_LAYER_CREATE;

// 返回
typedef struct {
    int32 p1;          // 层句柄，0 为非法
} T_DSM_COMMON_RSP;
```

`buffer` 由应用提供内存——平台不一定复制它，**模拟器实现时应该复制或持有引用**，
否则应用释放内存后图层内容就悬空了。

### 2.3 刷屏锁与 DMA

| code | 功能 |
|---|---|
| `mr_plat(1321)` | 设置刷屏锁（阻止中途刷屏） |
| `mr_plat(1322)` | 取消刷屏锁 |
| `mr_platEx(3009)` | DMA 异步刷屏（`MR_WAITING` + 轮询完成） |

模拟器实现：刷屏锁可以忽略（单线程渲染没有撕裂问题）；DMA 异步刷屏可以同步化
（直接返回 `MR_SUCCESS`，效果等价）。

## 3. 加速层：平台图片解码

应用自己带 PNG/JPG 解码太占空间，SkyEngine 提供平台解码（`x01x` 接口集起）：

| code | 功能 | 备注 |
|---|---|---|
| `mr_platEx(3001)` | 获取图片信息（宽高/格式） | |
| `mr_platEx(3002)` | 解码一张图片到指定缓冲 | GIF 不走这里 |
| `mr_platEx(3003)` | 查询解码状态 | 异步模式 |
| `mr_platEx(3004/3005)` | GIF 解码 / 释放 | GIF 逐帧 |
| `mr_platEx(3007)` | 绘制 BUFFER | |
| `mr_platEx(3010)` | 直接绘制图片到指定矩形 | 平台内部完成解码+缩放 |
| `mr_platEx(3011)` | 显示 GIF 动画 | |
| `mr_platEx(3014/3015)` | 绘制 MTK 资源格式的图片/GIF | 平台 ROM 内置资源 |

解码是异步设计（`MR_WAITING` → `3003` 轮询 → 回调）。模拟器同步化处理
（调用时直接完成，返回 `MR_SUCCESS`）没有发现问题——GIF 帧动画例外，
因为应用可能依赖帧间延时，需要模拟定时回调。

### 3.1 `MRAPP_IMAGE_DECODE_T`

手册 3002 页给出了结构名但**没有展开字段**（B 级缺失）。已知它包含源数据指针、
长度、目标缓冲、目标尺寸。实现时需要从真实应用的调用反推字段偏移——
这是目前文档化最不完全的接口之一（D 级，待补）。

## 5. 实现建议（D 级，来自 PymRP 实践）

1. **先做纯软件路线**：帧缓冲直写 + `mr_drawBitmap` 就能让 90% 的应用完整显示。
   图层系统和平台解码全部先返回 `MR_IGNORE`；
2. **帧缓冲用宿主原生 blit**：pygame 的 16 位 Surface 直接吃 RGB565，
   把 `mem[fb : fb+w*h*2]` 一次性灌进去，比逐像素快两个数量级；
3. **图层真要做**：按 `T_LAYER_CREATE` 保存一个 Surface 列表，
   在"刷屏"时机做 src-over 合成（透明值/透明色两个属性够用了）；
4. **GIF 动画**：如果实现，帧推进挂在 `MR_TIMER` 上，不要自己开线程——
   MRP 的世界是单线程事件驱动的；
5. **字库**：`mr_getCharBitmap` 返回的字模格式手册未详述，第一版可以先不做
   （应用大多用 mythroad 内置 GB 字库，那部分在 ARM 侧自己渲染）。
