# 19 sprintf、槽位表与 RX 列表里那个 "f"

> 2026-11-10 晚。老板看到 RX 管理器列表里多出一个字符 **f**（红箭头指着），
> 问：「你是不是没有实现 sprintf」。
>
> 结论先给：
>
> * 那个 **f 是一个完整、正常渲染的字母**（6×9 像素，衬线体），**不是乱码残留**，
>   也不是 sprintf 出错 —— 它在选中行右侧的固定列上，普通行同一位置是深色、
>   在浅色背景上看不见，选中行反白后才显眼。
> * 但老板的直觉**指向了一个真问题**：我们的 `sprintf` 一直有、但**残缺**，
>   而且**返回值给错了**（给字符数，C 标准要字节数）—— 中文文件名就会让
>   应用定位下一列时错位。`mr_sprintf` 确实**没实现**。这两条都补了。
> * 顺带挖出一件更值得记住的事：**我们的 mr_table 与 mrpoid 官方从 0x048 起
>   整表错位一格**（官方那里是 `mr_sprintf`）。目前无实际影响，但已固化探针。

---

## 一、那个 "f" 是什么：像素级取证

老板截图 271×359。我把高亮行右侧逐像素打印成字符画：

```
=== 高亮行 x=225..252 ===
  y=229  ~~~~~~~~~~~~###~~~~~      ← 顶部横
  y=230  ~~~~~~~~~~~#~~#~~~~~      ← 弯钩
  y=231  ~~~~~~~~~~~#~~~~~~~~
  y=232  ~~~~~~~~~#####~~~~~~      ← 中间横杠
  y=233  ~~~~~~~~~~~#~~~~~~~~
  y=234  ~~~~~~~~~~~#~~~~~~~~
  y=235  ~~~~~~~~~~~#~~~~~~~~
  y=236  ~~~~~~~~~~~#~~~~~~~~
  y=237  ~~~~~~~~~~####~~~~~~~      ← 底部尾钩
```

这是一个**完整的小写 f**（顶部弯钩 + 中间横杠 + 竖笔 + 尾钩），9 行高。

对比同一列的普通行：

```
=== 普通行 x=225..252 ===
  y=141  ++++++++++++....+++++++++++   ← 深色像素，是文件名末尾的 "p"
```

**普通行同区域是文件名最后一个字母 "p"**（`.mrp` 的 p），高亮行的文件名末尾
"p" 在 x=226，**x=234–239 处多了一个 f**。

于是有两条可能：

1. **文件名被画了两遍**（第二遍位置算错）；
2. **列表右侧本来就有一列属性标记**（f = file），普通行画成深色看不见，
   选中行反白成白色。

我倾向第 2 条，但**没法在本地复现验证**（见第五节），所以给老板一个
30 秒就能做的判定实验（见第七节）。

## 二、sprintf 的真实状态

| 项 | 状态 | 说明 |
|---|---|---|
| `sprintf`（mr_table 0x044） | **有，但残缺** | 不支持 `%f`；`%ld` 的 `l` 被当转换符吃掉，只剩 32 位；宽度/精度/左对齐基本没做 |
| `mr_sprintf`（MRP 专用版） | **没有** | 官方 mrpoid 的 0x048 槽位就是它 |
| **返回值** | **错的** | 返回 Python **字符数**，C 标准要**字节数** |

第三条最阴险：`sprintf` 写进内存的是 GBK 字节（`put_cstr` 用的 GBK），
但返回值是字符数。文件名里有中文时（老板列表里就有「2012红警战国」），
应用拿返回值定位下一列就会**短一截 → 错位**。

## 三、格式化器补齐清单

`impl.py` 的 `_fmt` 从 60 行的小函数重写成「解析 / 取参 / 渲染」三段：

```python
_parse_fmt(fmt)   -> [{"kind":"text"|"conv", flags, width, prec, lenmod, conv}, ...]
_collect(specs, get_int, get_q, get_f) -> {下标: (类型, 值)}
_render(specs, vals, mem) -> str
```

支持：

| 类别 | 支持 |
|---|---|
| 转换符 | `%d %i %u %o %x %X %f %e %g %G %c %s %p %%` |
| 长度修饰符 | `hh h l ll L j z t`（ARM AAPCS：**long 是 32 位**，long long 才 64 位） |
| 标志 | `-`（左对齐）`+`（带号）空格 `#`（0x/0 前缀）`0`（零填充） |
| 宽度/精度 | 数字宽度、`.N` 精度、`*` 动态宽度与精度 |

配套：

- `bridge.py::ArmCall` 新增 `qarg(n)`（栈上 64 位，8 字节对齐）与
  `farg(n)`（栈上 double，8 字节对齐）—— AAPCS 规定 64 位/浮点变参走栈；
- `sprintf` 返回值改为**写入的字节数**（不含结尾 null）；
- 新增 `mr_sprintf`（与 sprintf 同语义，已在 `impl` 注册；等槽位确认后即可挂表）。

> 一个坑：解析长度修饰符时**不能把 `q` 收进去** —— ARM 上 `%q` 不是转换符，
> 收进去会把 `%q` 整个吃掉（我第一版就踩了）。

回归：`tests/fmt_probe.py` **44 项**（基本转换符 / 宽度精度 / 浮点 / 长度修饰符 /
sprintf 端到端字节数 / mr_sprintf / 未知转换符不崩）。

## 四、槽位表与 mrpoid 官方的差异（顺手挖出来的）

官方 `mr/mythroad.c::_mr_c_function_table[]` 共 130 项。逐项对比我们的
146 槽 mr_table：

```
  0x000  官方=mr_malloc          我们=mr_malloc        ✓
  ...
  0x040  官方=strstr             我们=strstr           ✓
  0x044  官方=sprintf            我们=sprintf          ✓
!! 0x048  官方=mr_sprintf        我们=atoi             ← 从这里开始错位
!! 0x04C  官方=atoi              我们=strtoul
!! 0x050  官方=strtoul           我们=rand
!! 0x054  官方=rand              我们=reserve0
!! 0x058  官方=NULL              我们=reserve1
!! 0x05C  官方=mr_stop_ex        我们=_mr_c_internal_table
...
```

**前 17 项（0x000–0x040）完全一致**，从 0x048 起错位一格，112 项不一致。

### 4.1 为什么我们的表是这样

我们的顺序是**从 `cfunction.ext` 反推**的，不是抄 mrpoid：

- 官方 0x054 = `rand`、0x058 = `NULL`、0x05C = `mr_stop_ex`；
- 我们的 0x054/0x058 是 `reserve0/reserve1`（**槽位里写 0，不是函数指针**），
  0x05C 才是 `_mr_c_internal_table`。

这说明 **cfunction.ext 用的就是"没有 mr_sprintf、0x058/0x05C 是空洞"的版本**，
与 2018 年的 mrpoid 不是同一版布局。

### 4.2 为什么错位至今没暴露

三个原因叠加：

1. **MRP 应用不走 mr_table**：它们通过 **DSM 层 51 槽**（`dsm_require_funcs`）
   使用平台 API（文件、绘图、网络），mr_table 的 C 库槽位只是给 ext 用的；
2. **应用的 C 库由 ext 自己接管**：`_mr_c_function_new` 被调了两次 ——
   第一次是 ext 启动时交回 helper（`helper=0xA4088, len=20`），
   第二次是 **ext 内部自己实现的** `_mr_c_function_new(002DD3A0, 8212)`
   （`[arm]` 前缀 = ext 打的日志），应用把 8212 字节的 C 函数表注册给了 ext；
3. **实测 0x048–0x060 从不被调用**：dsm_gm / 曲奇 / 2048 / RX 管理器四个真实
   MRP 跑下来，mr_table 全部槽位只被调 4 次（`mr_malloc` / `memcpy` / `memset` /
   `_mr_c_function_new`），0x044–0x060 **一次都没有**。

### 4.3 风险与防护

隐患是真的：一旦某个 MRP 直接用 mr_table 的 C 库槽位（比如自己调 0x048），
它会调到我们的 `atoi` —— 语义完全不对，且**不报错**。

`tests/table_probe.py`（11 项）把这个事实固化：

- 0x000–0x040 必须与官方一致（防止悄悄漂移）；
- 0x048 起差异清单打印出来（快照区间内 20 项）；
- 0x054/0x058 必须是数据槽 0（ext 反推出来的真实空洞）；
- `mr_sprintf` 已在 impl 里待命。

**没有盲目改表**：在没有 ext 侧硬证据之前改 146 槽的顺序，风险远大于收益。
正确做法是等一份能确认 ext 期望布局的样本（不同版本的 `cfunction.ext`），
或者用 `mr_sprintf` 出现频率高的 MRP 来反证。

## 五、为什么本地复现不了老板的画面

RX 管理器启动时弹的是：

> 请点击"确定"**下载字库**，点击"取消"退出。

字库来自**斯凯服务器**（已停运）。我们的 runtime 里虽然有
`system/gb16.uc2`、`fonts/font16.tsf` 等文件，但 RX 要走自己的
`skyfont.ext`（包内 gzip，4487 字节）去下载/解压，下载失败就一直停在对话框 ——
**按任何键都没反应**（SELECT / DOWN+SELECT / SOFT_L 四种组合画面完全一致，
浅色像素都是 13661）。

所以老板那边能进列表，说明他环境里字库已就绪；我们这边进不去，
**没法做逐像素对照**。

## 七、给老板的 30 秒判定实验

在 RX 管理器里**选中另一个文件**（比如 `322025_240320_eslss.mrp`），看右侧那个
字符：

- **如果它跟着文件名变**（变成 "s" 或别的）→ 是「文件名被画了两遍」，
  位置在 RX 包内部的字符串拼接；
- **如果它始终是 "f"** → 是列表右侧的**文件类型列**（f = file），
  普通行是深色画在浅底上看不见，选中行反白才显眼 —— 属应用正常设计。

无论哪种，**都不是模拟器的 sprintf 出错**：RX 的格式化走的是它自己注册的
C 库（ext 内部实现），我们的 0x044 槽位在整个 RX 运行期间一次都没被调用。

## 八、边界与后续

- `qarg/farg` 按 AAPCS 近似（8 字节对齐取栈），寄存器区放不下的 64 位/浮点
  变参一律走栈；MRP 里这俩几乎不用（实测无应用调用 0x048 之后的槽位）。
- `sprintf` 的返回值改成了字节数，**这是行为变化**：若有应用原先依赖字符数，
  会受影响 —— 但按 C 标准字节数才是对的，且中文场景下字符数必然是错的。
- 官方表差异**暂不改表**，等 ext 侧证据。
- RX 本地进不去列表的问题（字库下载）仍未解决：斯凯停运后没有字库下发源，
  除非从真机导出 `skyfont` 相关缓存。
