# 05 · 声音与流媒体专题

声音是 MRP 里**接口形态最多、历史包袱最重**的子系统。这篇把两条播放通路
（外加一条 PCM 直写）讲透，并标出实现时必踩的坑。

---

## 1. 三条通路总览

| 通路 | 接口 | 模型 | 适用 |
|---|---|---|---|
| ① 一次性播放 | `mr_playSound` / `mr_stopSound` | 给一整块音频数据，播完为止 | 音效、短 BGM |
| ② 有状态播放器 | `mr_platEx(201x…216x)` | load → play → pause/seek → stop，像媒体播放器对象 | 长音乐、需要进度控制 |
| ③ PCM 环形缓冲 | `mr_plat(102/103)` | 应用自己写 PCM 到约定地址，驱动播 | 流式、合成音、自定义解码 |

三条通路**互相独立**，同一应用可能同时用（如 ② 播背景乐 + ① 播按键音效）。

---

## 2. 通路①：`mr_playSound`

### 2.1 签名（B 级，手册原文）

```c
int32 mr_playSound(int type, const void* data, uint32 dataLen, int32 loop);
int32 mr_stopSound(int type);
```

**四个参数**。第二个是**内存数据指针**，不是文件名——应用自己把文件读进内存再交给平台。
`loop != 0` 循环播放，`== 0` 单次。

> 常见误传：把 `mr_playSound` 理解成"播放一个 mid 文件"。
> 手册示例里 `data` 参数注释是"音频数据"，语义就是内存缓冲。

### 2.2 `type` 枚举：两版不兼容 ⚠️

这是**整套 API 里最阴的坑**。两份权威资料给出不同的枚举：

| 值 | 老版（mrpoid 原版 mrporting.h，5 值） | vmrp 版（7 值） |
|---|---|---|
| 0 | `MR_SOUND_MIDI` | `MR_SOUND_MIDI` |
| 1 | `MR_SOUND_WAV` | `MR_SOUND_WAV` |
| 2 | `MR_SOUND_MP3` | `MR_SOUND_MP3` |
| 3 | `MR_SOUND_AMR` | `MR_SOUND_PCM` |
| 4 | `MR_SOUND_PCM` | `MR_SOUND_M4A` |
| 5 | — | `MR_SOUND_AMR` |
| 6 | — | `MR_SOUND_AMR_WB` |

**值 3 和 4 的含义在两版里互换**。应用是按它编译时的头文件传值的，
所以模拟器**不能只看 type 参数判断格式**。

实用的消歧方法（A 级实测可行）：**看数据内容的魔数**。

```
"#!AMR\n"      → AMR（注意是 5 字节头）
"RIFF"         → WAV
"MThd"         → MIDI
"\xFF\xFB"/ID3 → MP3
其他           → 按老版枚举的 PCM（8K 裸 PCM）
```

（PymRP 的实现：`mrp_emu/audio/mixer.py`，`#!AMR` 判定要精确 5 字节——
我第一次写成 6 字节导致永远不命中。）

### 2.3 音量

`mr_plat(1302, level)` 设置播放音量。**注意这是 `x15x` 之后的接口集才有**
（见 [01 §5](01-三层结构与移植模型.md#5-接口跟踪表能力是按版本逐批加的)），
老机器上会返回 `MR_IGNORE`，应用必须能容忍音量控制不存在。

## 3. 通路②：`mr_platEx` 多媒体播放器

### 3.1 code 规则

`201x ~ 216x`，其中 **`x` 是媒体类型**：

| x | 类型 | 模拟器支持建议 |
|---|---|---|
| 1 | MIDI | ✅ 自研合成（SMF 解析 + 波表合成） |
| 2 | WAVE | ✅ RIFF 解析 + 重采样 |
| 3 | MP3 | ⚠️ 需 MP3 解码库 |
| 4 | AMR | ❌ 需 AMR 编解码器 |
| 5 | PCM | ✅ 直接喂缓冲 |
| 6 | M4A | ❌ 需 AAC 解码器 |
| 7 | AAC | ❌ 需 AAC 解码器 |

所以 `2042` = 播放 WAVE、`2011` = 初始化 MIDI 设备。

### 3.2 状态机

完整生命周期（B 级，手册 201x~216x 各页）：

```
201x  初始化设备（指定类型/采样率/声道）
202x  加载文件（传路径）  / 203x 加载缓冲（传内存数据）
204x  从当前位置播放
      ├── 205x 暂停    206x 继续
      ├── 210x 定位（秒）    211x 定位（字节偏移）
      └── 207x 停止
209x  查询状态
212x  总时长      213x/215x 当前进度
208x  关闭设备    216x 释放多媒体模块
```

### 3.3 查询状态的返回值

`mr_platEx(209x, ...)` 返回 `MR_PLAT_VALUE_BASE + 状态`（B 级）：

| 值 | 含义 |
|---|---|
| 1001 | IDLE |
| 1002 | INITED |
| 1003 | LOADED |
| 1004 | PLAYING |
| 1005 | PAUSED |
| 1006 | SUSPENDED |
| 1007 | SUSPENDING |

**这正是 `MR_PLAT_VALUE_BASE` 双重语义的典型现场**：`1001` 既是"成功且值为 1"
（如果按 `1000+1` 解释），又是 IDLE 状态。判断时必须**先查状态表再解释**，
见 [01 §2.3](01-三层结构与移植模型.md#23-mr_plat_value_base--最容易踩的语义陷阱)。

### 3.4 多通道

`222x`（加载）/`223x`（播放）/`224x`（停止）/`225x`（释放）支持同时挂多个音源，
参数里带通道号。游戏音效叠 BGM 的场景会用到。

### 3.5 实现建议（D 级，来自 PymRP 实践）

- **不要用宿主的"单实例 music 通道"** 实现 201x 状态机——状态机需要自己持有解码后
  的 PCM 和独立播放通道，否则状态查询（209x）会和音效（通路①）互相干扰；
- seek 最省事的实现是**重新切片**：记住加载的原始数据，seek 时从目标位置重新解压/重采样；
- 每个媒体类型一个播放器实例足够，用 `dict[type]` 管理。

## 4. 通路③：PCM 环形缓冲（`mr_plat 102/103`）

这是最底层的音频通路，把"混音/缓冲管理"完全交给应用：

```
应用侧                          平台侧
──────                          ──────
mr_plat(102, addr)   ──────►   记住"PCM 写入地址"
  （告知驱动写入地址）
往 addr 写 PCM 数据
mr_plat(103, 0)      ──────►   返回"已播放到的绝对地址"
  （查询播放位置）
播放位置和写入位置的差 = 待播数据量，应用据此决定继续写还是等待
```

要点：

- PCM 格式：8K 采样率（手册 `mr_playSound` 参数注释 `//8K`），
  具体位宽/声道以设备初始化时的约定为准；
- 这是**唯一支持真流式**的通路——应用可以边下载边播；
- 模拟器实现：一块环形缓冲 + 定时消费即可，`mr_plat(103)` 返回消费位置。

> 版本要求：环形缓冲接口属于早期接口，`x01x` 即有；但**背景播放**
> （切后台继续出声）是 `x15x` 才加的。

## 5. 录音（反向的音频）

| code | 功能 |
|---|---|
| `mr_platEx(2700)` | 开始录音 |
| `mr_plat(2701/2702/2703)` | 录音暂停/恢复/停止 |
| `mr_platEx(2704)` | 获取 PCM 数据 |

录音属于 `x08x` 接口集。模拟器可以直接返回 `MR_IGNORE`（没有麦克风场景）。

## 7. 排查声音问题的 checklist

1. **确认应用真的调了**：加日志看 `mr_playSound`/`mr_platEx` 是否被调用——
   不少老游戏只在特定场景（菜单音效）发声；
2. **看 type 值和数据魔数**是否一致（§2.2 枚举冲突）；
3. **检查 `mr_soundOn`**：mythroad 层有全局开关，为 0 时应用侧就静音了
   （C 级，mythroad.c 源码）；
4. **数据是否读完**：应用常用 `mr_open`+`mr_read` 读文件进内存，文件系统实现
   有 bug 时音频数据是残的，解码自然失败；
5. **通路② 状态机是否被"单例播放器"互相顶掉**（§3.5）。
