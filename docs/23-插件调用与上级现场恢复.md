# 插件调用与返回：恢复上级 MRP 运行现场

> 症状：调用任何插件，返回后都退回系统主界面；正确行为应是恢复上级 MRP 的运行现场。

## 一、真机的插件调用是「重启链」

真机（MTK mythroad 层，`ref/mrpoid/mr/mythroad.c`）里，**插件调用不是函数调用，而是一次 VM 重启**。
整条链都在 `cfunction.ext`（ARM 侧 mythroad 实现）内部闭环：

```
应用 Lua:  RunFile("ipqq.mrp", "startqq.mr", param)
   │
   ├─ MRF_RunFile()                      mythroad.c:5518
   │     pack_filename     = "ipqq.mrp"
   │     start_filename    = "startqq.mr"
   │     start_fileparameter = param
   │     mr_timer_p        = "restart"
   │     mr_state          = MR_STATE_RESTART
   │
   ├─ 下一帧 mr_timer() 命中 RESTART 分支   mythroad.c:7581
   │     mr_stop()                     → mr_stop_ex(TRUE)
   │     _mr_intra_start(start_filename, NULL)   ← 加载并运行插件 MRP
   │        └─ mr_open(pack_filename)  ← 用 RunFile 的第一个参数找包
   │
   └─ 插件 Lua:  Exit()
         └─ MRF_Exit()                   mythroad.c:5195
               if (old_pack_filename[0]) {          ← 上级现场存在？
                  pack_filename  = old_pack_filename
                  start_filename = old_start_filename
                  mr_state = MR_STATE_RESTART        ← 再次重启 → 回到上级
               } else {
                  mr_exit()                          ← 真退出，退回桌面
               }
```

上级现场由应用在调 `RunFile` 之前用 `TestCom1(3, "dsm_gm.mrp", ...)` 写进
`old_pack_filename`（`mythroad.c:6173` 的 case 3）。

`dsm_gm.mrp` 的 `start.mr` 就是标准范例（反汇编常量池可见）：
`RunFile` + `ipqq.mrp` + `startqq.mr` + `_strCom(3, "dsm_gm.mrp", ...)`。

## 二、我们踩的两个坑

### 坑 1：把 `mr_stop_ex` 当成了「退出应用」

我们原来把 `mr_stop_ex` 实现成 `vm.exited = True`（`api/impl.py`），
主循环一看到 `vm.exited` 就 `back_to_home()` 退到桌面。

但官方语义（`mythroad.c:7266`）里，`mr_stop_ex` 只做这些事：

* `mr_state = MR_STATE_IDLE`
* `mr_timer_state = MR_TIMER_STATE_IDLE`
* 停定时器、释放屏幕缓冲
* `freemem != 0` 时 `mr_mem_free(Origin_LG_mem_base, ...)`

**它不调 `mr_exit()`、不结束整个应用** —— 它只是重启链的一环。
真机上应用调插件时走的就是这条路，我们却在这里把整个会话拆了，
于是插件刚要启动就被判定成「应用退出」→ 退回主界面。

真退出到桌面只有两个入口，两者语义都正确，保持不变：

| 接口 | 槽位 | 语义 |
|---|---|---|
| `mr_stop_ex` | mr_table 0x058 | 停当前 MRP 实例（重启链一环） |
| `mr_exit` | mr_table 0x0D8 | 真退出 → 退回桌面 |
| DSM `exit` | dsm 0x08 | 真退出 → 退回桌面 |

### 坑 2：文件系统找不到插件包

ext 重启时用 `mr_open(pack_filename)` 加载插件包，`pack_filename` 是
`RunFile` 的第一个参数 —— 应用传的是**裸文件名**（`"ipqq.mrp"`）
或 `"plugins/netpay.mrp"` 这种相对路径。

真机上这些路径是相对 **MRP 安装目录 `mythroad/`** 的。
我们的 `fs.resolve()` 却只认 workdir 根目录，`"ipqq.mrp"` 被解析成
`<workdir>/ipqq.mrp` → 文件不存在 → 插件加载失败。

（`fs.work_path` 虽然由 `mr_platEx(1204)` / `dsmSwitchPath` 维护，
但 ext 内部自己处理路径切换，从不调我们的 1204，所以 `work_path`
实际上一直是空的 —— 靠它兜底指望不上。）

## 三、改了什么

### `mrp_emu/api/impl.py` — `mr_stop_ex` 语义修正

```python
@api("mr_stop_ex")
def mr_stop_ex(ctx, vm):
    """停止**当前 MRP 实例**（对应 mythroad/mythroad.c 的 ``mr_stop_ex``）。
    ...它不调用 ``mr_exit()``、不结束整个应用...
    """
    freemem = ctx.arg(0)
    vm.app.log(f"[mrp] mr_stop_ex 停止当前实例 (freemem={freemem})")
    vm.instance_stopped = True      # 只标记「本实例停止」
    ctx.ret(MR_SUCCESS)
```

`mr_exit` / DSM `exit` 维持 `vm.exited = True`（真退出）。

### `mrp_emu/vm.py` — 新增状态字段

* `app_stack`：MRP 应用栈。`push_app()` / `pop_app()` 保存与恢复上级现场
  （包名、入口、参数）。栈非空说明「当前是插件，返回后应回上级」。
* `instance_stopped`：`mr_stop_ex` 置位，由主循环消费。

### `mrp_emu/cli.py` — 主循环区分「停实例」与「退出」

```python
if mode == "mrp" and mrp_loaded and vm.instance_stopped:
    # mr_stop_ex：只停掉当前 MRP 实例，不等于退出应用。
    # 让 ext 自己在下一帧 timer 里完成重启。
    vm.instance_stopped = False
    log("[vm] mr_stop_ex：当前实例停止，等待 ext 重启链接管")
    continue
```

### `mrp_emu/fs.py` — 相对路径按真机目录解析

```python

    prefixes = []

    prefixes.append("mythroad/")
    for prefix in prefixes:
        ...
        # 只在命中**文件**时采纳（目录留给原路径语义）
        if ctarget.is_file():
            n = cand

```

顺序：当前工作路径 → `mythroad/`（MRP 包安装目录）→ workdir 根目录。
只在**目标是文件**时采纳，目录形态（`"."` / `"mythroad"` / `"plugins/"`）
保持原样，避免改坏「浏览目录」语义（RX 管理器依赖它）。

## 四、验证

新增 `tests/plugin_probe.py`（24 项）固化三条语义：

1. `mr_stop_ex` 只置 `instance_stopped`，**不**置 `vm.exited`；
   `mr_exit` / DSM `exit` 仍置 `vm.exited`。
2. `Vm.app_stack` 的 push/pop 行为。
3. 插件包路径解析：裸包名 → `mythroad/`；`plugins/xxx.mrp` →
   `mythroad/plugins/`；目录形态与穿越钳制不变。

回归：全套 21 个探针 rc=0、0 失败；
QQDSM2007 / QQ2010 / ghdljdb / RX管理器 四个真实应用运行无异常。

## 五、仍然存在的边界

* **完整的插件往返还需要真机交互才能端到端验证**：`dsm_gm`（游戏中心）
  的 `RunFile` 入口要先联网下载「阅读器」组件才会出现，本地没有，
  跑不到那一步。机制层面的三个断点（`mr_stop_ex` 语义、路径解析、
  应用栈）已逐个定位并修复，但「插件跑起来再返回上级」的完整往返
  尚未在本地复现过。
* `dsm_gm` 用的目标包 `ipqq.mrp` 本地不存在（真机上是 QQ 的另一个包），
  已确认 `RunFile` 的调用方式与 `old_pack_filename` 的保存方式，
  但没有可用的目标包做实测。
* 部分应用（如 QQ2007 的 `network.mr`、支付应用的 `payment.mr`）用
  `mr_platEx(0x90004, ...)` 这个**斯凯私有扩展码**调平台能力，
  手册里没有记载（只有 `0x90001` 时区、`0x90002` 语言列表），
  输入结构 48 字节。这条路目前仍返回 `MR_IGNORE`，
  ext 会打印 `[WARN]mr_platEx(code:589828, ...) not impl!`。
  若这条路径也涉及插件装载，需要拿到该结构的定义才能补齐。
